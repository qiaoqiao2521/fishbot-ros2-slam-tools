## 2026-10-06 offline passage postmortem
The user supplied an overhead oblique photo showing visible floor clearance beside the robot, questioned the excessive time spent at the opening, and reported that the robot is charging. No hardware, ROS, serial, network state or control configuration was changed for this review. The photo supports investigating an over-restrictive controller; it does not provide a calibrated width or establish clearance at lidar height.

Confirmed contributing mechanisms:
- Segment 25 through 59 includes 36 recorded attempts (20 turns, 13 advances, 3 reverses), with 22 completed and 14 aborted. File completion mtimes span 5627.39 s (93 min 47 s). Summed last motion-loop sample times are 102.05 s; stop observations total 184.58 s. The remaining elapsed time includes inter-command analysis, sampling preparation, code changes, reconnection and waiting, which cannot be precisely apportioned. The five-second stop setting was not the main source of delay. The short-segment orchestration was an unsuitable long-running passage strategy.
- The direct guard in tools/fishbot_guarded_mapping.py uses a fixed 0.34 m forward rectangle, half-width 0.27 m by default or 0.18 m for the teaching-model profile. It does not read the URDF, costmap inflation, or a Nav2 footprint. Any single valid scan point inside aborts the segment. Thus a 0.24 m-wide teaching model is judged against 0.36 m width after the model-profile change, or 0.54 m initially. This is a hard rejection boundary rather than a graded preference for more clearance.
- Replaying after-59-stationary.json finds two points inside the 0.36 m guard at approximately (0.2325,-0.1784) and (0.2346,-0.1768) m: only 1.63/3.22 mm over its right edge. The same snapshot contains 35 points in the original 0.54 m guard. These are post-stop observations, not the original triggering scan; a false alarm is not established. The private illustration work/review-20261006/guard-vs-model.png overlays these exact points and the teaching-model outline.
- The latest 0.20 m rotation circle is a separate check, including nonzero heading corrections. Stored after-32 through after-57 snapshots have no points inside this circle; no evidence supports blaming that circle for the later front-corridor stops. Earlier 0.25 m turn checks did abort two attempts.
- The guard assumes scan coordinates already equal body XY; it does not verify frame_id or transform through TF. The saved launch uses zero XY/yaw offset and z=0.02 m; the teaching URDF uses z=0.151 m and MuJoCo z=0.167 m. A z-only discrepancy does not explain the 2D lateral test, but actual mounting geometry remains unmeasured.
- Model geometry remains a teaching approximation: 0.24 m outer width and 0.20 m wheel separation, versus firmware source default separation 0.17275 m with persistent-board overrides. This mismatch is an audit target, not proof of the installed setting or of the variable yaw-error cause. The bounded physical passage did not run the MuJoCo/Nav2 path-following pipeline.
- Trigger diagnostics are insufficient: clearance rejection occurs before sample recording and only the error string is saved. Exact triggering scan, point IDs, source/receive ages, selected envelope and command must be captured to distinguish true clearance failure, noise and stale geometry.

Recommended implementation order, not yet implemented or physically accepted:
1. Measure outer body/wheel projections, lidar pose and effective wheel geometry; reconcile one authoritative geometry/TF source. Check left/right rotation and straight travel against an independent reference, without assuming a constant angular correction.
2. Reuse the existing Nav2 RPP baseline for continuous local path tracking during SLAM after real-platform validation. The agent should set a bounded target/path; a persistent local controller handles centering and small corrections at its own control rate. Avoid rebuilding/discovering a node for each few centimetres. Bound recovery attempts and report lack of progress instead of repeating dozens of micro-turns.
3. Separate measured footprint, clearance preference/slowdown, and hard collision stopping. Evaluate projected footprint and measured stopping distance/latency at current velocity. Use Collision Monitor approach/velocity-dependent zones, retaining source-time and loss-of-command protection. Neither dropping all single returns nor blindly changing min_points is justified: thin furniture legs must remain detectable. Any hysteresis/filtering must preserve timely hard-obstacle response. Standard costmap inflation is a graded field and should not all become forbidden space.
4. Record/replay trigger scans and display actual footprint, active stop/slow zones and triggering points in RViz. Reproduce this geometry with noise/heading perturbations offline, then validate one continuous physical pass, stopping distance and heading error after charging. Simulation success remains separate from real-car acceptance.
